Valentin — two engines behind one ALB

The architecture this change builds. One CloudFront distribution, one ALB, one DynamoDB table, one model — and two interchangeable agent engines selected by path so the same request can be served either way and measured. The left lane is what runs today. The right lane is new: a thin streaming proxy in front of AgentCore Runtime, Memory, Gateway and Observability.
Bedrock and DynamoDB are deliberately shared, not duplicated — that is what makes a latency or cost delta attributable to the orchestration layer instead of to a different model or a different store.

The seam already exists. AgentOrchestratorInterface in agent-orchestrator.ts is two methods wide, and StubAgentCoreAdapter has carried a TODO(yellow) since the first commit. Engine B is a second implementation of an interface the app already programs against — not a fork of the app.
Why a proxy at all. AgentCore Runtime cannot be an ALB target: ALB targets are instance, IP, Lambda or ALB, and the Runtime is a Bedrock API reached by InvokeAgentRuntime. A Lambda target could front it but cannot response-stream, which would destroy the time-to-first-token measurement. A second Fargate service can, and it runs the same image as engine A with one environment variable changed.
Memory does the work; DynamoDB keeps the record. AgentCore Memory owns the conversation and the managed preference extraction. Its retrieval API returns ranked natural language, not the typed fields the profile UI renders, and its records expire by design — so engine B mirrors what Memory extracted back into the same table, tagged engine=agentcore. One table means GET /api/session/:id/preferences and the profile panel work identically on both lanes, and both engines' output is scorable in one place.
Nothing on the right lane is deployed yet. Every value in the left lane was read from live AWS and the CDK; every identifier on the right is the name this change will create.
