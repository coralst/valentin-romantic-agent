Use case and what the app can do

The details arrive in conversation, months before they matter — and "anniversary" on the day is too late. So: extract, remember, act early.

1

Claude Sonnet 4.5 on Bedrock, in character.

2

3
He keeps the dates

You choose the lead time — a month, a week, a day.

4
The reminder arrives

Real email: restaurants, a playlist, a link to confirm.

FoodHobbiesMusic TravelGiftsLove language Important datesPersonality

Why an agent and not a form with a cron job: unstructured input over weeks, a plan whose next tool depends on what came back, and a human in the loop before anything sends.

04 · Architecture

Architecture — diagram

One URL, two engines, switchable from the UI. Same model, same guardrail, same table — so every difference is the platform.

Engine A · my glue code  →  Engine B · AgentCore
  • ECS Fargate → Runtime
    one always-on task → one microVM per session
  • DynamoDB → Memory
    my store → a managed strategy
  • A 2nd Bedrock call → Memory
    my extraction pass → extraction I don't write
  • In-process registry → Gateway
    functions → tools over MCP, on Lambda
  • span-bridge.ts → Observability
    hand-wired spans → OTEL, no wiring

Engine A · in-process registry

A function call inside the task

  • No authorization boundary
    anything in the process can call anything
  • One identity
    the task role is the agent and the app at once
  • Adding a tool
    redeploy the container
vs
Engine B · Gateway over MCP

A contract the platform holds

  • CUSTOM_JWT, the only inbound mode
    allowedClients scoped to two machine clients — a signed-in visitor's token opens nothing
  • Two callers, two credentials
    the agent's client and the app's, so the access log separates them
  • confirm_* hidden from the model
    only the proxy can spend money

Schemas are generated from the tools and a unit test fails on drift, so the two engines cannot disagree about what a tool accepts. exceptionLevel: DEBUG passes the tool's own validation error back to the model instead of a generic failure.

One guardrail, applied by both engines — that is what makes the comparison mean anything. What AgentCore added was identity, not policy.

Engine A · one role

The task is the boundary

  • One task role
    model, table and every integration secret
  • Guardrail in my code path
    if I forget the call, there is no guardrail
  • Profile lives until deleted
    no expiry by construction
vs
Engine B · Identity + Gateway + Memory

Four boundaries the platform holds

  • Workload identity per runtime
    scoped to workload-identity/valentin_agent_*
  • Secret never in a template
    the agent reads its own client secret at cold start
  • ApplyGuardrail granted separately
    from InvokeModel — the policy is its own permission
  • Memory expires in 90 days
    namespaced per session, so two partners never blend

13 · Lessons learned

Lessons learned

01
The workflow cost more than the product

32 of 57 PRs went into the agents, hooks and merge gate. Budget for building the process.

02
What AgentCore sold me was blast radius, not money

187× collapses to 13.5× once fixed costs amortise. The durable win is one microVM per session.

03
Plan with the strong model, execute with the cheap one

Stuck in a loop, more of the same model didn't help — a stronger planner did. Model choice is per-phase.

04
Don't trust "healthy"

Engine B was green for weeks and had never served a turn. Four faults, each hiding the next.
