02 · Use case

The date isn't the hard part. Remembering is.

You know her anniversary is somewhere in March. You know she mentioned a restaurant once, and that she doesn't eat fish. None of it is written down anywhere, and the gap between caring about someone and actually planning something is pure admin — which is exactly the thing that gets dropped.

The problem

The details arrive in conversation

Nobody fills in an eighteen-field questionnaire about their partner, and the details worth keeping aren't fields anyway — they're mentioned in passing, once, months before they matter.

Why a reminder app doesn't fix it

"Anniversary" on the day is useless

By then every good table is gone. What you needed was lead time you chose, and options you could act on in one tap — not a notification telling you you're already late.

What it actually is

Extract, remember, act later

Long-lived preference extraction, a durable profile, and a time-triggered outbound action. Romance is the demo. The pattern is onboarding, renewals and account-health follow-up.

The agent test — why this needs an agent and not a form with a cron job: the input is unstructured and arrives over weeks, the plan needs several tools in an order that depends on what came back (is that Friday a Shabbat? is the table free? is she vegetarian?), and a human has to stay in the loop before anything is booked or sent. No fixed decision tree survives that.

04 · Architecture

One product, two engines, one diagram.

Same agent, built twice, both running behind one URL and switchable from the UI. Same persona, same model, same reply call — so every difference belongs to the platform.

Engine A · glue code I wrote  →  Engine B · AgentCore
  • ECS Fargate → Runtime
    one always-on task → one microVM per session
  • DynamoDB → Memory
    my store and schema → a managed strategy
  • A 2nd Bedrock call → Memory
    my extraction pass → extraction I don't write
  • In-process registry → Gateway
    functions in the task → tools over MCP, on Lambda

Every box exists in us-east-1. Bedrock, the guardrail and one DynamoDB table are held fixed across both lanes — that's what makes a delta attributable to the orchestration layer rather than to a different model.

07 · Comparison · Tool use

The same twenty tools, reached two different ways.

This is the part that makes it an agent rather than a chatbot: it can look the world up, and it can offer to act on it. The tool surface is identical on both engines — how the agent is allowed to reach it is not.

20
tools, ten integrations

Ontopo · Amadeus · Google Calendar, Gmail and Places · Spotify · web search · a page reader · Hebcal · Wolt · WhatsApp. Live APIs, not stubs.

13
that only look things up

Availability, Shabbat times, Hebrew dates, places nearby, music. The agent plans around real constraints instead of inventing them.

7
that propose, never act

Every propose_* tool returns a card she confirms. It drafts the email and books nothing — a human is in the loop by construction.

5
model round-trips per turn

MAX_TOOL_ITERATIONS. It calls a tool, reads the result, and decides again — and it can ask for several at once, resolved concurrently.

Engine A · in-process

A registry inside the task

    called directly in the Node process
  • No authorization boundary
    anything in the task can call anything
  • Adding a tool
    redeploy the container
  • Fast and simple
    no network hop, no schema to keep in sync
vs
Engine B · Gateway over MCP

A contract the platform owns

  • Two Lambda targets
    3 profile tools + 20 integration tools
  • CUSTOM_JWT authorizer
    scoped to exactly two machine clients
  • Adding a tool
    regenerate schemas, update the stack
  • A hop, and a real seam
    the tool contract is reviewable, not implicit

The schemas engine B publishes are generated from the tools themselves by scripts/generate-tool-schemas.mts, so the two engines cannot drift apart — a tool added to engine A and forgotten in the Gateway is a build failure rather than a silently dark integration. That was learned the hard way: twice, a tool merged on main was missing from the Gateway's account. Honest edge — the WhatsApp nudge exists as a tool but the guardrail blocks PHONE, so that one path is deliberately unreachable today.

One fault. Forty sessions.

Cost is not the strongest argument for AgentCore — this is. Both sides are the same forty live sessions, one process-level fault injected into the same session on each.

Engine A

One Node process

Forty WebSockets in one Set, one heap, one event loop — attach-websocket.ts:31.

40

of 40 sessions lost
every user, and every partner profile in flight

vs
Engine B

One microVM per session

Forty sessions, forty isolated execution environments. The fault has nowhere to travel.

1

of 40 sessions lost
the other 39 never notice

Unhandled rejection

One turn throws without a handler; Node exits, taking all 40 sockets with it.

Out of memory

One runaway conversation exhausts the 1 GiB task. The OOM killer doesn't ask whose request it was.

Event-loop block

One synchronous hot spot stalls the single loop — the other 39 see the app stop.

Injection that pivots

Reaches a process-wide singleton — the Bedrock client, the tool registry — holding everyone's credentials.

Two limits, both real. Engine A does isolate per-user state (forUser) — one user's logic bug can't read another's data; what they share is the process. And engine B isn't fully isolated in this deployment either — it still answers through valentin-ac-proxy, one shared Fargate task holding the sockets. The right panel is what AgentCore Runtime gives you, not yet what this repo deploys.

09 · Comparison · Security

One guardrail, both engines — and it's tuned, not switched on.

This app asks a stranger for another person's name, birthday and home address, stores them, and then mails them. The interesting security work wasn't turning a guardrail on; it was discovering that the safe default broke the product, and measuring where the line actually belongs.

6
content filters, measured

SEXUAL is MEDIUM on input, HIGH on output — at HIGH it blocked "her ring size is 6 and she is 5 foot 4", which is a profile field the agent asks for outright.

5
PII entities blocked

Card number, SSN, phone, AWS access key, AWS secret key. Nothing about remembering a birthday is a reason to carry a credential.

3
regexes replacing one entity

ADDRESS read "she's been saving for Kyoto" as an address. Three residence-shaped patterns block 42 Maple Street and let Paris through.

7
tools that cannot act alone

Every write — reservation, email, calendar, gift — is a proposal with an expiry, awaiting a human yes. The agent's own word is never sufficient authority.

Engine A

Trust inside the process

The guardrail is applied in my code, tools are function calls, and one compromised turn sits in the same heap as everyone's credentials. Per-user state is scoped by forUser; the process is not.

vs
Engine B

Boundaries the platform enforces

Same guardrail via bedrock:ApplyGuardrail, so the policy can't diverge. Tools sit behind a JWT-scoped Gateway, each session gets its own microVM, and the Gateway signs Lambda calls with its own role rather than the agent's.

Known gap · ALB listener is HTTP

TLS terminates at CloudFront; the hop to the ALB isn't encrypted. Fine for a demo, not for anything real.

Known gap · Cognito isn't enforced

The user pool exists and the Gateway uses it for machine auth, but the app's own front door is a demo login, not a real one.

Known gap · secrets by hand

Google OAuth lives in Secrets Manager deployed and .env locally, and populating it is still a manual step after a deploy.

The judgement call worth defending: NAME, AGE, ADDRESS and EMAIL are deliberately not blocked. They are this agent's subject matter — the first two facts it asks for, and a recipient address is a required argument to propose_email — and each is stored under its own owner's key. Anonymising them made the agent answer "{NAME} — that's lovely" seconds after being told her name. Every one of those decisions is a dated comment in infra/lib/safety-stack.ts with the sentence that failed and the guardrail run that proved it.

12 · Conclusions

Four things I didn't know going in.

01
The workflow cost more than the product

32 of 57 PRs and +13,425 lines went into the agents, hooks, router and merge gate — more than the application itself. If you try this, budget for building the process, not just the thing the process makes.

02
What AgentCore sold me was blast radius, not money

The cost table is the loud slide and the weaker argument — the ratio collapses from 187× to 13.5× once fixed costs amortise. The durable win is one microVM per session: the same fault that takes out forty sessions on Fargate takes out one.

03
Plan with the strong model, execute with the cheap one

When an agent got stuck in a loop, more of the same model didn't help — a stronger model writing the plan did, then a weaker one executing each step. Model choice is a per-phase decision, not a per-project one.

04
Don't trust "healthy"

Engine B was green for weeks and had never served a turn. CREATE_COMPLETE, a healthy Runtime, and a proxy logging invoke ok: true — while the container returned its failures as a 200 with an empty body. Four faults, each hiding the next.

Honest scope, since it's the part worth trusting: the orchestrator-led loop, the turn router, the eight hooks and the merge gate are real, unit-tested and exercised across the whole PR history. The agent labels are convention applied in a batch, not a wired-up hook. And engine B's isolation is what the Runtime offers — this deployment still answers through one shared proxy task. Every claim here is checkable: the methodology writeup, the generated graph, and all 57 PR conversations.
