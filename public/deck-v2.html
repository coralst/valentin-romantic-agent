Part 2 · Who really built it

Control advances by a call, never by hope.

The first design was event-led: an agent posted “Ready for Review” and the flow waited for a hook to fire. It never worked — the loop had no engine. Now the master drives every turn by calling the next agent and waiting for it to return.

Turn 1

Master reviews, then tags

Reads the diff and the CI result, posts one comment naming @backend-dev and @qa-agent.

Turns 2–7

Both agents, at once

invokeSubAgent() twice from that one comment. Backend pushes fixes, QA runs the browser suite, each replies — then returns. A sub-agent never re-invokes the master, so the call graph stays shallow.

Turns 8–10

Decide, then the gate

Master reads every return. Blockers left → another round. Otherwise it posts the approval token and calls merge_pull_request — where a hook is waiting.

lastWordIsMasterallTaggedResponded isApprovalciGreen all four, or the merge is refused

On the GitHub side: three workflows and exactly four required checks — tsc --noEmit, Vitest, Vite build, Playwright. Part 3 · What I learned

Four things I didn't know going in.

01
Event-led orchestration doesn't work

My first design had agents post “Ready for Review” and wait for a hook to wake the next one. Kiro hooks aren't GitHub webhooks, there's no webhook back in, and the poller's dispatch was a no-op. Agents finished and the conversation just stopped. The loop had no engine — control has to advance by a call.

02
Put guardrails where judgement is weakest

Models are good at writing code and bad at deciding whose turn it is. So routing and merges aren't model output — they're four pure, offline, unit-tested functions. A refused merge is a feature: 6 of 57 PRs were closed unmerged.

03
Disjoint ownership is the whole unlock

Parallel agents are only safe if no two can write the same file. Every prompt carries an explicit do-not-modify list. That single constraint is what turns five simultaneous agents from a conflict generator into a team.

04
The workflow costs more than the product

32 of 57 PRs and +12,443 lines went into the agents, hooks, router and gate — more than the app itself. If you try this, budget for building the process, not just the thing the process makes.

Bonus, learned the hard way: GitHub returns 422 if you approve your own PR, and every agent here shares one account — so the approval had to become a token in a comment, enforced by a pre-merge hook, with the branch ruleset requiring green CI.

Part 3 · What I learned

What's wired up, and what's only convention.

Real

The orchestrator-led loop, turn router, 8 hooks, and merge gate Implemented, unit-tested, and exercised across the whole PR history

Convention

Agent labels exist on every agent-owned PR — but were applied as a batch The auto-label script is a proposal, not a wired-up hook. Branch prefixes drifted too: feat/arch-, not feat/architect-

Limited

invokeSubAgent is unavailable in supervised mode, and infra needed a seventh lane nobody planned The master drives turns manually; hooks still apply, so the guardrails hold — the automation doesn't
