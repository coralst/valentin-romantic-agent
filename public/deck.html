The premise

Six agents, one real GitHub workflow,
a human with a veto.

Give six agents distinct personas, distinct file ownership, and a real workflow — issues, branches, draft PRs, review threads, CI, merge — and see whether what comes out is coherent.

01
Agents do the work

Every pull request here was opened, reviewed and merged by an agent. Ownership is enforced by prompt, not politely suggested.

Each persona is a real prompt file in .kiro/agents/ with a written voice exemplar and an explicit do-not-modify list. Disjoint ownership is what makes parallel agent work safe — without it, five agents editing at once is just a merge-conflict generator.

The call graph

Hub and spoke, not a recursive tangle.

Dashed arrows down are invokeSubAgent() calls; bold arrows up are plain returns. A sub-agent returns to the master rather than re-invoking it — the return is the hand-back. That's what keeps this shallow instead of a tangle where nobody knows who's waiting on whom.

The lifecycle

Five phases, spec before build.

Defined in a steering file every agent reads. Spec comes first — nobody branches until the architect's spec is approved. The dotted self-arrow on phase 3 is another round, and it fires often. Red CI doesn't fail the PR; it reopens the review loop.

The failure behind the fix

The first design didn't work.

The original loop was event-led: a sub-agent finishes, posts “Ready for Review”, and the flow depends on a hook or poller waking the next agent. It never worked once.

  • Kiro hooks are not GitHub webhooks — different trigger surface entirely
  • There is no webhook back into Kiro, so GitHub can't wake an agent
  • The poller's dispatch step was effectively a no-op
  • Agents finished their turn and the conversation simply stopped
  • The loop had no engine.

Full post-mortem in .kiro/analysis/. I'm showing the failure because the fix only makes sense against it.

The engine

Orchestrator-led: control advances by a call.

The par block is genuine fan-out: the master tags two agents in one comment, invokes both, and collects both replies before deciding. At-mentions are still there — but now they're a readable transcript and a parseable routing signal, not the trigger.

The determinism layer

Guardrails where judgement is weakest.

Routing and merge decisions are not left to the model. Four pure, offline, fully unit-tested functions guard the two fragile boundaries: each hand-off, and the merge.

parseTurn(comment)

Who spoke, who's tagged, is this terminal. Returns nextActors as a list — that's what makes fan-out expressible rather than round-robin.

lastWordIsMaster(thread)

The master must close the thread. No merging out from under an open reply.

allTaggedResponded(thread)

Nobody left hanging. A tagged agent that never answered blocks the gate.

evaluateConversationGate(…)

The backstop: valid approval token + last word + green CI, or no merge.

A refused merge is expected behaviour, not a bug. Source: .kiro/skills/pr-monitoring/

A real-world wrinkle

You can't approve your own pull request.

Every agent here, master included, acts under the same GitHub account. GitHub refuses a self-approval — so a formal approval stalls the merge forever, waiting on something that can never happen.

$ gh api --method POST …/reviews -f event=APPROVE
HTTP 422 · "Can not approve your own pull request"
The fix

Gate the merge on an approval comment containing the exact token APPROVED-BY-MASTER-AGENT, checked by a pre-merge hook.

Quality still enforced

The branch ruleset requires passing CI rather than a formal review state. The hook is what makes the token trustworthy rather than decorative.

Honest scope

Convention

Drift

Unplanned

So what did they build?

Conversation in. Structured profile out.

  • You know her birthday. You half-remember the restaurant. Then you're buying a candle again.
  • Forms don't fix it — nobody fills in 18 fields about their partner, and the interesting details aren't fields.
  • So Valentin runs a warm, unhurried interview instead.
  • Eight categories: food, hobbies, music, travel, gifts, love language, important dates, personality.
  • Every entry carries a confidence score, and the panel fills in live as you talk.

Shown here is the seeded demo profile — all 18 fields, grouped into Basics and Relationship, with a calendar surfacing the next important date.

How it works

One message, four moves.

1
You type

The message travels over a session-scoped WebSocket to the Express gateway, which routes it to the orchestrator.

2
Valentin replies

Bedrock's Converse API returns a reply in character, with the context window kept trimmed and coherent.

3
Extraction runs

A second Bedrock call uses tool-use to pull structured preferences out of the same message — off the reply's critical path.

4
Profile updates

Preferences are persisted, pushed back over the same socket, and highlighted as they land.

Step three is the load-bearing decision: extraction is asynchronous, so the chat never waits on it. The stack underneath — React 19 + TypeScript strict on Vite · Express 5 with a ws gateway · claude-sonnet-4-5 on Bedrock · DynamoDB behind a storage interface · CDK for ECS Fargate, CloudFront and Cognito · Vitest and Playwright for tests.
