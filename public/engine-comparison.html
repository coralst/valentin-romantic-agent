Where the money goes

The same bill, broken into its parts

One shared scale, so the 59× is the thing you see first. Engine A's bill is two items: a Fargate task that runs whether or not anyone is talking to it, and a second Bedrock call on every single turn. Engine B has neither.

Does it flip at scale?

No. There is no crossover.

An always-on floor usually amortises — that's the standard rebuttal, and it does not apply here. Engine A's per-turn cost is also ~17× engine B's, because of the extra Bedrock call. So it starts higher and stays higher: the gap narrows from 59× to 17× and then stops narrowing. Both axes are logarithmic.

What this does not claim

Where AgentCore loses

Stated because it's true — and because it's what makes the rest believable

  • AgentCore Runtime is 2.20× dearer per hour than Fargate for identical resources. It wins on billing granularity, not on unit price.
  • AgentCore Memory is ~124× dearer per turn than DynamoDB. It loses this layer outright. It doesn't change the answer only because the layer is $0.375 of a $0.42 bill — DynamoDB on-demand is so cheap that beating it is worth almost nothing.
  • This compares two architectures, not the current deployment. The repo today runs both engines side by side as a measurement harness, which costs more than either alone. Comparing that to itself would prove nothing.
  • AgentCore does not remove Fargate here. A same-sized proxy task still fronts it, deliberately, so latency stays comparable. Nor does it remove DynamoDB — the Gateway's Lambda reads and writes the same table.
  • Latency is not on this page. No measurement of either engine exists; every duration in the repo is authored. Engine A makes up to 5 sequential Converse round-trips on a tool turn against engine B's one call, so the direction is genuinely unknown.

Read this before quoting the numbers

Six assumptions

Rates are sourced; these six inputs are not measurements

  1. Bedrock Sonnet 4.5 at $3 / $15 per MTok. The Anthropic table on the Bedrock pricing page is JS-rendered and did not load, so this is an assumption. The $6.66 extraction line scales linearly with it — halve the rate and the total becomes $21.35, still 51× engine B.
  2. 3 seconds of Runtime time per turn. No measurement exists. Conservative: it charges CPU for the whole turn, while AWS states I/O-wait CPU isn't charged, and an agent turn is mostly waiting on the model.
  3. Memory retrievals bill per API call, not per record returned. The decisive unknown — see the sensitivity note below.
  4. The built-in strategy's extraction model is inside the $0.75/1k records. The pricing page distinguishes built-in from "self-managed … plus model usage in your account", which implies it is. Our IaC also grants memoryRole bedrock:InvokeModel, which hints it might not be.
  5. Extraction call ≈ 2,940 input + 300 output tokens, derived from the 7,519-char tool schema plus the untrimmed history at 4 chars/token.
  6. 500 turns/month as this app's traffic. The chart above covers 500 to 500,000.

Sensitivity — the one that could flip a layer. If "$0.50 per 1,000 retrievals" meters per record rather than per call, then ListMemoryRecords at MAX_MEMORY_RECORDS = 100 costs $0.05/turn, engine B's per-turn cost becomes 3.8× engine A's, and the monthly total at 500 turns rises from $0.42 to $25.17 — roughly parity. That constant is ours to lower, and the repo never calls RetrieveMemoryRecords at all. Confirm this before presenting.
