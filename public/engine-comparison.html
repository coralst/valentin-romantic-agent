Glue code vs AgentCore

The same agent, the same model, the same prompts — served two ways. Engine A is the hand-built stack: Bedrock Converse from a Fargate service, with conversation memory and preference extraction we wrote ourselves. Engine B is AgentCore Runtime, Memory and Gateway. This page is what the difference actually costs.

Reply latency — AgentCore is slower

And it should be: InvokeAgentRuntime is a second network call wrapping the model call, and tools go out over MCP to a Lambda instead of the in-process SDK. This is the cost of the trade, stated plainly.

The other side

Where glue code wins

Reasons not to move — stated because they're real

  • Above roughly 40k turns a month, the always-on tasks are cheaper. A flat floor amortises; per-invocation billing does not.
  • Latency is lower and always will be. One fewer network hop is one fewer network hop.
  • Propose-then-confirm exists only on engine A. confirmAction throws on the AgentCore orchestrator — booking a restaurant behind a click is a feature engine B has not got yet.
  • No preview-service dependency. Converse and DynamoDB are generally available with published limits.
  • Every failure is debuggable in one process. The hand-written tool loop is five iterations of code you can read; a managed Runtime is not.

What is real on this page: the 727-line count (re-counted from the repo by a unit test that fails if it drifts), the model-calls-per-turn difference, the always-on task count from the CDK, and the component lists. What is a placeholder: every dotted value — latencies, store reads, tokens, and all dollar figures.

Filling them in needs the deployed dev app and one bench run per engine, because one process serves one engine (AGENT_ENGINE is per-process by design) and Bedrock is blocked for the local IAM user.

AgentCore here still answers behind a Fargate proxy. What it removes is the stateful Fargate, the hand-written extractor and the DynamoDB memory layer — not Fargate.
