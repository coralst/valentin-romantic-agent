What can go wrong when agents review each other.

Before any of the guardrails existed, this is what a six-agent team on one repository actually does. None of these are hypothetical — each one either happened here or was one turn away, and every one of them merges cleanly and silently.

Eight ways the workflow breaks itself · the state of things before the hooks

The loop has no engine

The first design was event-led: a sub-agent finished, posted “Ready for Review”, and the flow waited for a hook to fire. But Kiro hooks are not GitHub webhooks, there is no webhook back into Kiro, and the poller's dispatch was effectively a no-op.

Symptom: the PR sits at “Ready for Review” forever. Nothing errors. Nothing moves.

The agent marks its own homework

An agent that decides for itself when it is finished will decide it is finished. Lint, unit tests and the build are one prompt away from being skipped, and “looks right to me” is not a check.

Symptom: red CI discovered after the merge, by a human.

Work starts before there is a spec

The fastest path from a request to code is to write the code. No Issue, no acceptance criteria, no design anyone agreed to — and, given the chance, straight onto main.

Symptom: a large diff nobody can review against anything, because nothing was ever stated.

Two agents open the same file

Parallel branches are the whole point of having six agents, and they are exactly what lets two of them edit the same module from two different mental models of it.

Symptom: a semantic conflict that git merges without complaint, because textually there was nothing to resolve.

The thread dangles

The last comment on the PR is a sub-agent's. It says the work is done. Nobody with authority ever said whether that was accepted.

Symptom: reading the thread later, you cannot tell an approved PR from an abandoned one.

A tagged agent is never heard from

The master tags two agents in one comment. One replies. The review reads as a conversation, but half of it never happened.

Symptom: the merge proceeds on half a review, and the missing half is the one that would have run the browser.

A comment tags nobody

A non-terminal comment with no at-mention leaves no next actor. It is not a conclusion and it is not a hand-off; it is a dead end that looks like progress.

Symptom: a stall, with no error raised anywhere, indistinguishable from an agent still thinking.

An approval that can never arrive

Every agent here — the master included — acts under the same GitHub account, and GitHub refuses to let an author approve their own PR: 422 Can not approve your own pull request.

Symptom: gate the merge on a formal approval and you wait on something that is not merely late, it is impossible.

Two more that follow from the same root: a skipped required check reads as “not failed”, so a path-filtered CI job can wave through an untested PR; and if a sub-agent is allowed to re-invoke the master, the call graph stops being a hub and starts being a recursion. Every item on this page is a place where model judgement was load-bearing — which is exactly where it should not be. See what replaced it →

Eight hooks, and a loop that drives itself.

Control advances by a function call, never by hoping a trigger fires — and the two fragile moments, the hand-off and the merge, are decided by pure offline JavaScript rather than by the model.

Step 4 The merge gate

merge_pull_request is intercepted, not executed. Four conditions, or the merge is refused.

pre-merge-conversation-gate

A sub-agent never re-invokes the master; the return is the hand-back, so the call graph stays a shallow hub-and-spoke. The at-mentions are still the human-readable transcript and a machine-parseable routing signal — they are just no longer the trigger.

The gate's four conditions · evaluateConversationGate(), pure and unit-tested

✓
lastWordIsMaster

The master holds the final comment. No PR conversation may end on a sub-agent's turn.

✓
allTaggedResponded

Every sub-agent that got tagged actually replied. Nobody is left hanging.

✓
isApproval

That closing comment carries the exact token APPROVED-BY-MASTER-AGENT.

✓
ciGreen

All four required checks passed — and a skipped check counts as unsatisfied, not as fine.

A refused merge is a feature, not a bug. { mergeable: false, reasons: [...] } is the expected output whenever the conversation isn't actually finished. The corrective turn is always the same: make sure every tagged agent has replied, then post the closing comment so the master holds the last word. Only then is the merge retried.

The eight hooks · .kiro/hooks/ · all enabled

pre-task-arch-checkpreTaskExecution

Blocks a task from starting unless the Issue exists with acceptance criteria, the architect posted a spec and the master approved it, a Draft PR is open carrying Resolves #N, the branch isn't main, and the agent actually owns the paths it is about to touch.

post-task-ci-reviewpostTaskExecution

Runs lint → test → build, then machine-checks the changed files for ownership violations, naming, and secrets. The agent doesn't get to declare itself done.

route-turn-after-commentpostToolUse

Fires on every add_issue_comment and create_pull_request_review. Parses the comment, routes the next turn to whoever was tagged, recognises a terminal master comment — and flags a stall when a non-terminal comment tags nobody.

pre-merge-conversation-gatepreToolUse

Intercepts merge_pull_request itself and refuses the merge unless all four conditions above hold. This is the backstop the whole loop leans on.

monitor-pr-after-readyuserTriggered

Detaches a per-PR poller that watches for new reviews and comments, logging each one so a hand-off can be reconstructed after the fact.

handle-pr-feedbackuserTriggered

Reads the parsed feedback file, hands each blocker to the agent that owns the file, and makes it reply in its own voice rather than posting a checkbox list.

push-and-notify-pruserTriggered

Commits and pushes feature-branch work — never main — then posts PR status and a review request to the master and starts monitoring.

stop-pr-monitoringuserTriggered

Kills the poller for a PR and clears its marker, state, signal, and log files, so a merged PR stops consuming a watcher.

Hooks gate and prompt; they never write the comment — prose quality comes from the voice exemplar in each agent's prompt. And a fifth CI job re-tests the workflow automation itself, so changing a hook has to prove it didn't break the loop.
